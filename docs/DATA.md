# DATA

The structures the system relies on (`database/schema.sql`, dated `database/migrations/`). Plain words; the point is the reasoning.

| Structure                                                 | Shape                                                                                                                                                                                    | Read / write pattern                                                                 | Size                | Who writes / reads                        |
|-----------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------|---------------------|-------------------------------------------|
| `announcements`                                           | PK `(symbol, filing_date)`                                                                                                                                                               | Written by ingestion, read by filing routes                                          | one row per filing  | ingestion writes; API reads               |
| `financial_snapshots`                                     | PK `(symbol, filing_date)`, amounts as columns (`total_debt`, `cash_equiv`, `revenue`, `interest_income`, `dividend_income`, `accounts_receivable`, `liquid_assets`, `non_halal_income`) | Upserted by ETL; joined with `governance_overrides` (`COALESCE(go.x, fs.x)`) on read | one row per filing  | ETL writes; engine inputs                 |
| `governance_overrides`                                    | PK `(symbol, filing_date)`                                                                                                                                                               | Admin upsert; overrides win over extracted values for **every** user                 | small               | admins write                              |
| `market_data_snapshots`, `bhavcopy_quotes`                | PK `(symbol, captured_at)` / `(symbol, trade_date)`                                                                                                                                      | Append/upsert by market-data resolver; latest read                                   | grows daily         | jobs write                                |
| `filing_evaluations`                                      | PK `(symbol, filing_date)`, `is_compliant BOOLEAN` (nullable), `verdict TEXT`, `ratios JSONB`, `market_cap_used`, `trailing_cap_used`, `evaluated_at`                                    | Upserted by API and jobs; read by filing and history routes                          | one row per filing  | engine output; **stale until recomputed** |
| `data_quality_issues`                                     | `UNIQUE (symbol, filing_date, issue_type)`, `resolved_at`                                                                                                                                | Recorded on anomalies / market failures; open issues push a filing to `needs-review` | small               | API/jobs write                            |
| `users`, `user_sessions`                                  | `user_sessions.token` = SHA-256 digest                                                                                                                                                   | Login/logout, per-request lookup                                                     | grows with users    | API                                       |
| `user_subscriptions`, `razorpay_orders`, `payment_events` | `payment_events` has a **unique `(provider, event_id)`** index                                                                                                                           | Webhook insert is idempotent                                                         | grows with payments | Razorpay webhook + API                    |
| `feedback_reports`, `feedback_events`                     | `public_token` unique                                                                                                                                                                    | Public create; admin triage                                                          | small               | public/admin                              |
| Watchlists (`watchlist_entries`) | Postgres, PK (user_id, symbol, trigger), FK to `users` with cascade | Insert-if-absent; baseline and flip by conditional `UPDATE` (seed first, then flip) | small | API (paid users) |

## Trade-offs worth defending
- **`(symbol, filing_date)` as the key** keeps one evaluation per filing, so a recompute overwrites in place. That is why history cannot be audited unless PR-B exports a before/after CSV first.
- **Verdict in two columns** (`is_compliant` boolean and `verdict` text): the boolean stays for old consumers and is `NULL` for unknown; the text carries the full state (`compliant`, `non-compliant`, `insufficient-data`, `needs-review`).
- **File-backed watchlists** are simple and fine for a pilot; they do not scale across hosts.
- **Ratios as JSONB** keep each evaluation self-describing (value, threshold, passed, note, provider).
